## Portable installation and backup

Privately transfer the same JSON to each family device using the owner's chosen private file channel. Open `catalog.html` on GitHub Pages in **Safari**, select the JSON once from Files, verify the 263-person status and five image previews, then open `app.html` and select a set. Do not publish or paste the JSON into a public URL. `catalog.html` also exports its current IndexedDB `active` record as a JSON backup for migration. The exported file includes names, official URLs and candidate ID mapping; it is sensitive even though it contains no image bytes. A private backup is required because Safari storage can be cleared. Each device imports separately; there is no account, server sync, device-bound key, public asset bundle or automatic remote update. The Pages UI never uploads the JSON to GitHub. A genuine session should be completed on iPad Safari before claiming real-image QA.

## Schema and invariants

- `schema_version=3`, `master_version`, `snapshot_frozen_at`, `source_checked_at`; the master describes the current approved view at that version.
- Each `candidate_master[]` retains `candidate_id` for the existing app and `identity_id` as the permanent person key. Initial `identity_id` equals the existing candidate ID. `identity_source_keys[]` records official profile references, **not** an instruction to replace identity if a URL changes. A Junior→STARTO transition reuses `identity_id` after human review and records a source alias; it must not create a second person.
- `current_affiliation` records current category/group with separate `category_evidence` and `group_evidence`. The label for a Junior without listed group is a catalog status, not a claimed group. `affiliation_history[]` is currently empty: no historical joining/debut dates were inferred. Future entries can be `{change_type, old_state, new_state, evidence}` with `evidence={source_type,source_url,observed_at,effective_at|null,status}`; secondary or unverified sources remain distinguishable from official observations. Preserve prior entries on later changes.
- `image_evidence` records the official listing and `source_listed_not_usage_clearance` status. `image_status=source-listed` retains its earlier narrow meaning. No person image bytes are in this repository or the master JSON.
- `candidate_sets.{STARTO_SELECT,JUNIOR_SELECT,ALL_SELECT}` contains frozen `version`, `frozen_at`, `ids[]`, and source URLs. Set IDs partition the master using the same person identities. A later approved master issues new set versions; it never mutates the old JSON.
- At session start the existing app copies `setId`, `setVersion`, `masterVersion`, `visualMode=NORMAL`, timestamps and the candidate name/category/group/profile/image fields into `selectionSnapshot`. This preserves the then-visible reveal even if the active master changes. Affiliation history remains in the master data layer; the old selection snapshot is not retrospectively enriched. FACE_ONLY may use the same identities and sets with a distinct visual-mode session later; no face processing is performed now.

## Future monthly Candidate Watch boundary

The watch is **not running**. A later independent read-only process may compare official STARTO/Junior individual and group listings against an approved master: new/disappeared profiles, category/group/member changes, debut announcements, name/profile URL/image URL changes. It should produce a proposed change report with `identity_id`, change type, old state, proposed state, source URL/type, observed/effective dates, confidence/status and affected sets. No difference means no notification. Any difference is reported for human review. Only an explicit **「Masterへ反映」** action may create a new private master and set versions. Disappearance alone must not silently delete an identity. Source outage or parse failure is a watch error, not a membership deletion. The watch does not write IndexedDB, session storage or Selection Engine state. Historical backfill and automated monthly scheduling are separate work.
